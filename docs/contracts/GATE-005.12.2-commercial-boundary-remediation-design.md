# Gate 5.12.2 — Commercial Boundary Remediation Design

**Status:** DESIGN FINALIZED 🔒  
**Type:** ARCHITECTURE DESIGN (ZERO CODE MUTATION)  
**Opened:** 2026-09-23  
**Follows:** Gate 5.12.1 (Legacy Commercial Inference Bypass Audit)  
**Precedes:** Gate 5.12.3 (Implementation & Verification)

---

## 0. Context & Mandate

Gate 5.12.1 proved that while the `Opportunity Engine` (DBPG/QIG) correctly computes opportunities based on Evidence, it is entirely disconnected from the downstream `SalesService` and `OfferMatcher`. Instead, LLM-generated heuristics (weaknesses, ai_opportunities, lead_score) act as a bypass, dictating Offer selection.

The mandate for this Gate is to design the architectural remediation that permanently severs the LLM from commercial decision-making and establishes the Opportunity Engine as the sole authority for Offer matching.

**This is a DESIGN ONLY gate. No code or database changes occur here.**

---

## Part I: The Four Core Contracts

### Contract A — Opportunity Authority
There is **exactly one** authoritative source for commercial opportunities: `evaluateProductionOpportunities()`.
No other component, service, or LLM prompt is authorized to assert, infer, or inject a commercial opportunity into the system.

### Contract B — Offer Eligibility
`OfferMatcher` may only score and rank offers based on:
1. `validated OpportunityOutput` (from Contract A).
2. `verified Evidence` (e.g., identity, capabilities, technologies).
It must **never** consume or reward points for LLM-generated insights, weakness strings, or abstract opportunity tags.

### Contract C — LLM Boundary
The LLM is strictly a **descriptive and generative engine**.
- It **CAN**: describe, summarize, and write sales copy based on verified facts.
- It **CANNOT**: create an Opportunity, authorize an Offer, or influence an Offer's relevance score.

### Contract D — Historical Data Immutability
Legacy data (`analysis_items` of type `AI_OPPORTUNITY`, `AUTOMATION_OPPORTUNITY`, `WEAKNESS` and existing `generated_messages`) remains as an immutable historical record. 
However, its **commercial eligibility is officially set to zero**; it must never re-enter the commercial pipeline or influence future Offer matching.

## Part II: Implementation Design

### 1. New OfferMatcher Input Contract
`OfferMatcher` will be refactored to consume a strict, typed interface that completely excludes LLM text and scores:
```typescript
interface OfferMatchingInput {
  category: string | null;
  capabilities: { type: string; value?: string | null }[];
  technologies: { category: string; name: string }[];
  opportunities: readonly OpportunityEvaluationOutput[]; // NEW: The only opportunity source
}
```

### 2. Opportunity → Offer Boundary
Instead of scanning LLM string arrays, `OfferMatcher` will check if an offer's required opportunities are present in the `opportunities` array.
- The `OfferMatcher` must consume the **Opportunity contract** (normalized status), not become a second Opportunity Engine. It will not hardcode rules like `if (opportunity.rule_slug === 'RULE-OPP-DBPG-001')`. Instead, offers will declare their capability/opportunity compatibility.
- An offer can only receive a match score for an opportunity if the `OpportunityEvaluationOutput` status is `OPPORTUNITY_DETECTED`.

### 3. Removal of LLM Commercial Inputs
The following methods will be **deleted** from `OfferMatcher`:
- `matchWeaknesses()` (-45 max pts bypass removed)
- `matchAiOpportunities()` (-20 max pts bypass removed)

### 4. `lead_score` Separation
The +10 bonus for `lead_score >= 70` will be **deleted** from `OfferMatcher`. 
`lead_score` will be removed from the `OfferMatchingInput` entirely. It remains exclusively a Prioritization Signal for UI sorting and urgency.

### 5. Legacy Data Treatment
- **No DB Purge:** `analysis_items` generated by the LLM remain in the DB.
- **Severance:** `getFullAnalysis()` or `SalesService` will no longer pass `analysis.weaknesses` or `analysis.ai_opportunities` to `OfferMatcher`. The data is orphaned from the commercial path.

### 6. `generated_messages` Provenance Treatment
Future generation requests will embed a provenance marker to distinguish between legacy bypass messages and Opportunity-gated messages.
- New messages will include metadata indicating they were generated via `OPPORTUNITY_GATED` logic (tracked implicitly by code versioning or a generation_source tag, without altering the DB schema).

### 7. `evaluateOpportunities()` Deprecation Strategy
- The legacy stub `evaluateOpportunities(evidence)` in `engine.ts` will be **deleted**.
- `analysis-service.ts` will be updated to correctly call `evaluateProductionOpportunities()` with the required state atoms.

### 8. Evidence Snapshot Boundary (Production Integration)
`generateSales` must evaluate Opportunities deterministically against a persisted, versioned Evidence snapshot. It must **not** trigger fresh website crawling, Evidence extraction, LLM opportunity inference, or commercial inference. Any new Evidence requires a new enrichment/scan lifecycle and a new immutable Evidence snapshot.
```text
Scan / Analysis
      ↓
Evidence Extraction
      ↓
Persisted Evidence Snapshot
      ↓
                         ┌─────────────────────┐
generateSales ──────────►│ Opportunity Engine  │
                         │ deterministic       │
                         └─────────┬───────────┘
                                   ↓
                         OpportunityEvaluation
                                   ↓
                              OfferMatcher
                                   ↓
                              Sales Assets
```

## Part III: Testing & Rollback

### 9. Contract Tests (Adversarial)
Gate 5.12.3 will introduce strict adversarial unit tests proving the `Opportunity → Offer` boundary:
- **Test A:** `Opportunity = []`, LLM weakness = "needs website" → Offer score = 0
- **Test B:** `Opportunity = []`, LLM ai_opportunity = "automated lead nurturing" → Offer score = 0
- **Test C:** `Opportunity = []`, `lead_score = 99` → Offer score = 0
- **Test D:** `Opportunity = []`, `capabilities = [...]` → Offer score = 0 (if capabilities alone don't prove opportunity).
- **Test E:** `Opportunity = DBPG`, LLM says "website is weak" → Only DBPG-authorized offer becomes eligible.
- **Test F:** `Opportunity = QIG`, LLM says "needs nurturing" → Nurturing offer cannot become eligible.
- **Test G (Commercial Invariance):** Varying the LLM copy completely (Analysis A, B, C) while keeping `Evidence` and `OpportunityEvaluationOutput` constant must yield the exact same `Offer` ranking.

### 10. Replay Tests
We will replay a known business (e.g., مجمع نهج الطبي) through the new `OfferMatcher` to mathematically prove that `Automated Lead Nurturing` is no longer recommended, and only Evidence-backed offers surface.

### 11. Rollback Strategy
If the integration breaks the UI or API, the rollback is simple:
- Revert `OfferMatcher` to its legacy state (restoring LLM string matching).
- Restore the legacy `evaluateOpportunities` stub.
- No DB migrations are required, making rollback instantaneous via Git.

### 12. Impact on Gate 5.10/5.11 Monitoring
Gate 5.13 (Production Monitoring) remains on **HOLD**.
Once Gate 5.12.3 is deployed, the Sales UI will accurately reflect the Rule Engine's output. Only then will the monitoring runbook (Gate 5.11) accurately measure the real-world impact of the DBPG/QIG rules.
